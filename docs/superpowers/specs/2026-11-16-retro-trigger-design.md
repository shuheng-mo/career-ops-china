# 复盘线：自动触发 + 复盘报告草稿 — 设计

日期：2026-11-16
状态：已与用户确认，待出实施计划

> 本仓库是公开仓库。本文只描述机制；真实数字、公司名、投递编号只出现在运行时生成的 gitignored 文件里（`data/retro/`）。

## 1. 意图

候选人用「投递 → 正面回复」转化率判断策略是否失灵。现有 `npm run pulse` 的红黄绿信号回答的是「回复数是否低于历史期望」（泊松模型，任何回复都算，基线是重启前全部历史），**它不回答用户真正关心的问题**：

> 近两周投出去的岗位，正面回复率有没有掉到我状态最好那个月的水平以下？掉了就停下来复盘、调策略，不要继续在僵尸岗和「静默失效」岗上浪费时间。

一次手工复盘（2026-11-16）证明了这条线有用：它发现了方向结构、渠道失效、评分与回复倒挂、规则把最对口的岗位压分等问题。本设计把这件事自动化：**自动判断该不该复盘 → 醒目且必达地提醒 → 一键生成证据齐全的报告草稿 → 结论由 Claude 和用户在对话里填。**

报告的读者是 Claude（后续会话），所以报告必须**全部基于 tracker 数据、每个比率写成 `x/n (%)`、关键结论附投递编号、口径写清楚**。

## 2. 目标 / 非目标 / 反目标

**目标**
- G1 每天自动计算复盘线，跌破即触发
- G2 触发提醒必达（不依赖用户手动跑任何命令），且比所有其他提醒（跟进任务、日历、日报）更醒目
- G3 `npm run retro` 生成一份 Claude 可直接读的报告草稿，证据部分自动、可复现
- G4 未处理前持续提醒；写出复盘报告后自动停止，并有冷却期

**非目标**
- 不自动下结论、不自动改规则、不自动结案。脚本只摆证据；判断在对话里做
- 不替换 pulse 现有的泊松信号（两者回答不同的问题，并存）
- 不回填历史报告缺失的字段（如旧报告没有「可达性」就标「未标注」）

**反目标（做成这样就算失败，哪怕「能跑」）**
- 提醒混进飞书跟进任务里（用户明确否决：会和追进度的任务混在一起，优先级被拉平）
- 拒信被算作「回复」，把官网系统拒信当成正面信号
- 报告里出现没有出处的结论，或把猜测写成事实
- 真实公司名 / 投递编号 / 个人信息进入公开仓库的被跟踪文件

## 3. 已决定的部分

### 3.1 复盘线（指标）

- **样本**：`appliedAt` 落在 `[today-27, today-14]` 的投递（即最近两周投出、且已满 14 天的批次）。未满 14 天的不算「没回」
- **样本不足**：n < 10 时，窗口起点每次往前扩 7 天，最多扩到 `today-55`（共 6 周）。仍 < 10 → 状态「数据不足」，不触发
- **正面回复**：`firstResponse ∈ {HR沟通, 约面}`，或 `furthestStage` 存在且不是 `未面`。**拒信不算**
- **基准**：`config/profile.yml` 新增 `retro.baseline_month`（用户状态最好的那个月，`YYYY-MM`），基准 = 该月投出的投递的正面回复率，**每次从 tracker 现算，不写死数字**
- **触发条件**：窗口正面回复率 **严格低于** 基准
- 数据只经 `tools/tracker-backend.mjs` 的 `listApplications()` 读取（md / bitable 后端透明）

### 3.2 触发后的状态机

- **按状态、不按边沿**：每天检查；只要「复盘线在线下」且「最近一份复盘报告早于本轮触发」，当天就提醒。错过一天（关机）第二天照样发
- **「已完成的复盘报告」的定义**（实施者决定）：`data/retro/*-retro.md` 中**不含**占位标记 `待 Claude 与用户填写` 的文件。`npm run retro` 生成的草稿带这个标记，所以**生成草稿不算复盘**，不会解除提醒、也不会启动冷却；只有对话里把解读 / 调整 / 下次问题三节填完、删掉标记后才算。2026-11-16 的手工报告没有这个标记，算已完成
- **解除**：出现日期 ≥ 本轮首次触发日的「已完成的复盘报告」→ 本轮结束
- **冷却**：最近一份「已完成的复盘报告」在 14 天内 → 不触发（调整需要时间在数据里显现）
- 状态存 `data/retro/.alert-state.json`（gitignored，随 `data/retro/`）：首次触发日、最近提醒日、连续天数、最近一次发送的 message_id

### 3.3 提醒通道（必达 + 最醒目）

1. **挂在已有的每天 9:00 launchd 任务上**（`com.career-ops.followup`，跑 `tools/feishu/followup.mjs`）：在跟进对账之前先做复盘线检查。复盘检查失败不能影响跟进对账，反之亦然。**不改 plist**
2. **飞书：机器人单独发一条消息**（不夹在日报或任务里），走 `notify.mjs` 已验证的 bot → 本人 p2p 路径（`--as bot`，`self_open_id`，idempotency key 按天 + 用途区分）。内容：标题「🟥 复盘线触发」、窗口正面回复率 `x/n` vs 基准 `x/n`、窗口日期、已连续触发天数、下一步 `npm run retro`
3. **对这条消息发飞书应用内加急**（`im.messages.urgent_app`，bot 身份，`user_id_type=open_id`，对象 = 本人）。加急是唯一比日历/任务更强的提醒级别
4. **日报**：`npm run feishu:digest` 运行时，若复盘线处于触发状态，把它放在日报最顶部（在现有「投递脉搏」之前）
5. **能力开关**（实施者决定）：新增独立 capability `retro_alert`（加进 `capabilities.mjs` 的 `KNOWN_CAPABILITIES`、`profile.yml` 和 `profile.example.yml`，默认开），**不复用 `im_card`** —— 关掉日报不应顺带静音复盘提醒，且加急可能需要 `im_card` 没有的 scope
6. **兜底**（`retro_alert` 关闭、发送失败、或加急失败）：macOS 系统通知（`osascript display notification`，带声音）+ 追加一行到 `data/reminders.md`。加急失败但消息已发出时，也要发系统通知，并在日志里说明原因（多半是缺 scope）
7. **Claude 侧**：`.claude/skills/career-ops/SKILL.md` 的路由前加一条：读 `data/retro/.alert-state.json`，处于触发状态时，任何 `/career-ops` 调用都先把复盘提出来，再做用户要的事

**scope / 权限约束**：加急需要的 scope 实施时用 `lark-cli auth scopes` / `auth check` 查准，**不要凭记忆写**。缺 scope 时不自行开通、不加 `--yes`；打印需要的 scope 和授权流程，交给用户。所有 lark-cli 调用只走 `tools/feishu/capabilities.mjs` 的 `runLarkCli()`（见 CLAUDE.md「lark-cli 集成铁律」）。

### 3.4 `npm run pulse` 的输出

在现有信号之后加一段「复盘线」：窗口日期、窗口正面回复 `x/n (%)`、基准 `x/n (%)`、状态（正常 / 触发 / 冷却中 / 数据不足）。复盘线的计算放在可单独导入的函数里，pulse、日报、9:00 检查、retro 共用同一份实现。

### 3.5 `npm run retro`：报告草稿

输出 `data/retro/{YYYY-MM-DD}-retro.md`。同名文件已存在 → 拒绝覆盖，提示 `--force`。即使复盘线没触发也能手动跑（用户随时可以要求复盘）。

**结构**（参照 2026-11-16 手工报告）：

1. **头部**：读者是 Claude 的说明；触发原因（复盘线数值，或「手动」）；口径（数据源、拉取时间、样本筛选、正面回复定义、批次定义、粗分说明）
2. **总量**：三列批次对比 —— 基准月 / 复盘线窗口 / 重启后全部（满 14 天）。每列：样本、任意回复、正面回复、回复中拒信数；附各批正面回复的编号列表
3. **分维度对比**（每个维度一张表，列 = 上述批次，单元格 = 正面回复 `x/n (%)`）：
   - 渠道
   - Track（空值按 CLAUDE.md 约定视为 `ai-app`，并在表下注明）
   - 方向：notes 带 `数据Agent` 标记的 vs 不带；历史行没有标记时退回关键词粗分，并标明哪些是粗分
   - 评分段：≥4.0 / 3.5–3.9 / <3.5 / 无分
   - 可达性：从 report 头 `**可达性：**` 解析；没有 → 「未标注」
   - Tier：从 report 头 `**Tier：**` 解析首字母（A/B/C/D）；没有 → 「未标注」
   - 回复类型分布：拒信 / HR沟通 / 约面 / 无
4. **清单**
   - 结案候选：`Applied`、无首次回复、投递 > 14 天（编号、公司、岗位、渠道、天数）。只列，不改
   - 待投队列：`Evaluated` 且过投递闸门，按可达性（高 > 中 > 低 > 未标注）再按 Score 排序。闸门（实施者决定）用 `modes/_shared.md` 的**完整 fit × Tier 表**（含 bridge × Tier C 不投），Tier 从 report 头解析；Tier 未标注的行按 Tier A/B 档（宽松档）判并在行尾注明「Tier 未标注」
5. **上次的待验证问题**：把最近一份旧复盘报告里「下次复盘要回答的问题」一节原样搬入，每条后留空让对话填答
6. **留空的三节**，标题后注明「待 Claude 与用户填写」：解读、调整、下次复盘要回答的问题

**小样本标注**：任何 n < 5 的单元格加 `（样本小）`，避免一两个回复被读成趋势。

## 4. 留给实施者的部分

- 模块拆分与文件名（建议：复盘线计算 + 报告渲染一个模块，提醒发送一个模块），只要满足「一份计算实现、多处复用」
- 测试形式：沿用仓库现有风格（`tools/test-*.mjs` 独立脚本 + `npm run test:*`）。至少覆盖：正面回复判定（拒信不算）、窗口扩展、触发 / 冷却 / 解除的状态转换、report 头解析缺字段时的回退
- report 头解析的具体正则（tracker 的 `report` 字段是 `[num](reports/...)` 形式的 markdown 链接）
- 系统通知的具体文案
- 日期一律用北京时间（与 `pulse.mjs` 一致）；复盘检查放在 `followup.mjs` 的跟进对账**之前**（对账在 `task` 能力关闭时会提前 return）

## 5. 验收

- 用当前 tracker 数据跑 `npm run pulse`，复盘线显示「触发」或「冷却中」（2026-11-16 已有手工报告 → 应为冷却中）
- `npm run retro -- --force` 生成的总量表，与 `data/retro/2026-11-16-retro.md` 的手工数字在口径一致处相符（手工版的批次按自然月切分，自动版按窗口切分，对不上的地方要能用口径差异解释）
- 用 `--dry-run` 跑 9:00 检查，能看到将要发送的消息体和加急调用参数，且不真正发送
- 删除冷却条件（临时改日期）后，检查会触发、会写 `.alert-state.json`、第二次同日运行不重复发送
